# 可靠性与多 Agent 价值诊断 v1

这是 v4 之后新增的开发诊断协议。v4 的来源、参考答案、原始运行和指标保持冻结。新用例针对已经观察到的问题，因此不是未见测试集；不得把用例针对性、一次成功或较高任务数宣传成普遍质量优势。

## 需要回答的两个问题

1. 多 Agent 的独立核查和补查是否真的把错误断言改成有证据、保留条件的正确答案，而不是只增加“未知”？
2. 来源更新或进程中断后，能否保留正确工作并减少重复请求，同时给出符合新资料的答案？这是运行效率与恢复能力，需要与报告质量分别展示。

v4 的实际起点是：24 次均完成；72 条价格里 43 条通过金额/币种/月年单位窄审、20 条有资料却撤回、9 条只有计费原则。90 条 SSO 相关结论仍有 2 条冲突断言与 2 条答案覆盖缺口。旧正则参考分数不是全文事实准确率。

## 小型挑战组

| 场景 | 所有架构收到的资料 | 关键验收 | 多 Agent 可能有用的环节 |
|---|---|---|---|
| `challenge-current-conflict` | 30 份合成来源；同日安全说明与发布记录对团队 SSO 相反 | 引用双方；明确冲突；statement、value、比较表及近期变化不能单方确认套餐范围 | 独立核查把局部结论与另一来源比较，再修订全部受影响字段 |
| `challenge-faq` | 30 份合成来源；安全页指向 FAQ，套餐与生效日期只在 FAQ | 找到 FAQ 并给出套餐和日期；已有答案时仅撤回不算完成 | 协调员根据缺口产生定向补查，核查员验证新证据 |
| `challenge-update-before` → `challenge-update-after` | 从相同 30 份资料开始，只把 `senyu-security` 更新为十月版本，明确替代九月说明 | 当前团队与企业 SSO 均支持且日期为 10 月 1 日；其余公司的正确事实保持一致；旧报告不改变 | 依赖追踪只使受影响结果失效，修订保留不相关工作 |

前两组来源分别复用 v4 的冲突与 FAQ 场景，以便直接复核旧失败类。更新组是新诊断。模块 `briefforge.reliability` 仅提供来源，不读取参考答案。`seed_reliability` 创建内部合成工作区；`apply_reliability_update` 只提交一个新的来源版本。

质量比较至少包含前两组 × single/pipeline/multi，共 6 次新运行；资源允许时预先确定相同的重复次数，不能只重跑失败的一方直到成功。更新比较另记初次报告与后续修订的费用，至少 3 组初次报告 + 3 次更新。若新增“全量重跑”效率对照，必须事先分配预算，且最终来源完全相同。没有全量重跑对照时只证明复用机制，不能声称节省了某个百分比。

## 公平运行与冻结

- 使用同一个模型 profile、相同文本/顺序/问题/维度/来源日期、相同单次费用与请求上限。各架构特有的角色、核查和补查属于待比较的系统差异，应透明记录。不能只给 multi 更多资料、暗示答案或放宽限制。
- 运行前调用 `freeze_reliability_manifest` 固定来源和独立 spec 的 SHA256，并记录 engine/provider/评分模块 SHA256、模型名称、provider 路由、预算、并发与参数。模型非确定性意味着小样本不支持统计结论。
- 同一场景各架构交错运行；共享 PostgreSQL 预算账本。不得新建临时账本规避已用预算。仅父任务执行付费请求。
- 保存所有原始报告、来源快照、任务/事件、失败、重试、修复次数、费用和耗时。超时/失败留在分母，不能只比较成功报告。重试受同一上限约束。
- 独立参考文件 `data/evaluation/reliability-v1/*.json` 只交给离线评分器。源码与导入链应证明研究引擎没有读取它。新指标写新文件 `metrics-v2.json`；评分工具拒绝覆盖，不回填旧历史成绩。

## 事实指标 v2

`score_fact_report(report, spec)` 按六个独立事实义务评价每个场景：三个价格、三个 SSO。每个义务同时看 statement、value、conditions；SSO 再检查同公司其他维度以及比较表的相关断言。

| 指标 | 含义 | 不能替代什么 |
|---|---|---|
| claim_presence | 是否有对应结论 | 不能代表回答问题 |
| answer_coverage | 是否回答义务、保留规定条件；预期未知可以是正确答案 | 已有答案却撤回为未知不得分 |
| evidence_completeness | 引文存在，并含所需金额/单位/套餐/日期；指定 FAQ 或冲突双方时确实引用 | 引文存在不代表结论一致 |
| fact_accuracy | 义务已回答、证据完整且没有检测到矛盾字段或错误引用 | 不是整篇报告准确率 |
| retained_assertion_issue_facts | 规则检测出错误选项或字段不一致的义务数 | 是待独立复核的问题，不能当通用语义识别器 |
| withdrawn_facts | 撤回至未知的义务数 | 撤回是安全行为，不自动算修正或覆盖改善 |
| review_required_facts | 未完整通过的义务数 | 不匹配可能是合法改写，需人工逐项复核 |

价格规则区分年付月均价格与相同金额年费，并检查月付价格、未含税和企业询价边界。冲突义务需要双方证据，value 不能在正文承认冲突后仍选一方。不能靠在 conditions 塞入正确短语来掩盖错误 statement 或 value。

规则是透明的有限模式匹配，不是语义真值机器。未解析改写、历史归因和复杂否定可能产生漏检或误报；最终报告仍需要不依赖系统核查器的人工语义审阅。正文摘要、建议和机会假设不在这六项评分范围内，应单独列限制。

`score_transitions(before, after, spec)` 将同一来源集合、同一义务下的中间稿与终稿分为 corrected、regressed、withdrawn_without_answer、unchanged_correct、unresolved。中间稿必须取自真实任务输出，不能人工注入错误或给 single 虚构一个前稿。没有可审计中间稿时报告 unavailable。来源更新前后的比较应注明知识已改变，不能把新事实当作原核查器纠错。

`compare_outcomes` 比较配对事实分数、覆盖、额外 confirmed/reserved 费用、请求数和耗时；缺失或不同的来源/spec/profile 哈希会拒绝给出可比差值。失败运行质量分按零计算，费用保留。保留占款与已确认费用分别报告；队列等待未单独量测时明确耗时包含它。

## 来源更新与崩溃恢复的独立验收

来源更新：记录修改前后来源 ID/版本、失效 claim ID、复用任务的原 ID/输出 hash、实际新增请求和最终事实。相同输出文本本身不是缓存命中证明，必须有运行记录证明该任务没有再调用模型。所有架构最终质量按 after spec 评分；同时报告未受影响事实的保持情况。

进程崩溃恢复是另一个运行机制测试。先预先指定可观察阶段，在部分任务已持久化、尚未完成报告时终止自己的 worker，再从同一 run/账本恢复；验证已完成任务 ID/输出 hash 不变、没有重复付费请求、run 最终完整、费用仍同账本。不能把改变资料和恢复旧 run 混为一谈；已冻结的 run 不应在恢复时悄悄读取新来源。

单 Agent 通常没有同样数量的中间任务，因此不能把“第两个子任务完成后”当作三架构等价故障点。可用各自“研究产物已持久化、终稿尚未提交”的逻辑阶段；若某架构没有该阶段，就单独陈述恢复能力的结构差异，不造一个不公平失败对照。

## 最终展示口径

先给全部配对运行结果，再选一个已通过独立审阅的具体过程示例：初稿错误/缺证据 → 核查发现问题 → 补查读到新证据 → 终稿各字段一致。若 multi 只降低错误断言却增加弃答，应同时展示这一代价。若 single 的覆盖或正确率更好，照实报告；多 Agent 的价值可以是可追踪纠错和恢复机制，不需要虚构总分优势。

新评测可用以下离线命令生成单份新指标（不会运行模型）：

```powershell
.venv\Scripts\python.exe -m briefforge.evaluation_v2 --report <新报告.json> --spec data/evaluation/reliability-v1/challenge-faq.json --out <新目录>/metrics-v2.json
```
